1. Executive Summary

Quantiva is a production-grade, full-stack web platform developed for the GitHappens (GitHappens), Defence Research and Development Organisation (DRDO). It serves as an interactive research and education platform for quantum algorithm simulation, experimentation, and visualization.

The platform bridges the gap between Quantum Engineers/Data Scientists (who write Jupyter Notebooks with Qiskit) and End Users (researchers, students, and analysts who interact via a modern web dashboard). Users can learn about quantum computing concepts, configure algorithm parameters through a UI, execute quantum circuits on an IBM Qiskit Aer simulator backend, and visualize results — including quantum circuits, histograms, Bloch spheres, and measurement probabilities — all within the browser.

Key Capabilities

  • Quantum Algorithm Execution: 12 pre-built quantum algorithms (Deutsch, Grover, Shor, QFT, VQE, etc.) runnable with custom parameters
  • Python Sandbox: A full in-browser code editor for writing and executing arbitrary Python/Qiskit code
  • 3D Bloch Sphere Visualization: Interactive WebGL-based quantum state visualization using Three.js
  • Circuit Simulator: Drag-and-drop quantum gate builder with real-time state vector computation
  • Circuit Challenges: Gamified puzzle system for building circuits that match target output states
  • Entanglement Lab: Bell State creation and measurement visualization
  • Content Management System: Full CMS for Documentation, Blogs (with likes/comments), News, and Courses with video lectures
  • Live News Feed: Real-time quantum computing news via GNews API integration
  • Admin Dashboard: Comprehensive analytics, user management, and content management panel
  • Google OAuth + JWT Authentication: Dual authentication with role-based access control
  • Dark/Light Theme: Seamless theme toggling via CSS Variables

3.3 Data Flow

The system follows a decoupled client-server architecture:

  1. Frontend (SPA) is served as static files from Vercel's CDN. All routes are rewritten to index.html via vercel.json.
  2. API Calls are made via Axios to the Express backend on Render. Every authenticated request includes a Bearer <JWT> header.
  3. Quantum Execution: When a user runs an algorithm, the backend spawns a Python child process using child_process.exec(), which runs papermill to execute the relevant .ipynb notebook with user-provided parameters. Output images and text are extracted from the executed notebook and returned as JSON.
  4. Image Uploads: In development, images are saved to backend/uploads/. In production, they are uploaded to Cloudinary via multer-storage-cloudinary.

The .env file contains all secrets (MongoDB URI, JWT secret, Cloudinary credentials, API keys). This file must NEVER be committed to version control or shared publicly. It is included in .gitignore.

8. Authentication System

8.1 Authentication Flow

Traditional Login (Username + Password)

  1. User submits username & password to POST /api/auth/login
  2. Backend finds user by username, compares password via bcrypt.compare()
  3. If valid, generates JWT containing {id, username, role} with 7-day expiry
  4. Frontend stores JWT in localStorage under key qsl_token
  5. Axios interceptor attaches Bearer <token> to all subsequent API requests
  6. On page refresh, AuthContext calls GET /api/auth/me to re-validate the token

Google OAuth Flow

  1. User clicks "Sign in with Google" → Google popup opens
  2. User authenticates with Google → Google returns an ID Token (credential)
  3. Frontend sends the ID Token to POST /api/auth/google-login
  4. Backend verifies the token using google-auth-library against the registered GOOGLE_CLIENT_ID
  5. If user email exists in DB → login. If not → create new user with a random password and default placeholders
  6. Returns JWT same as traditional flow

8.2 Role-Based Access Control (RBAC)

RolePermissions
userView dashboard, run algorithms, use sandbox, view content, like/comment blogs, take challenges
adminAll user permissions + Create/Edit/Delete algorithms, docs, blogs, news, courses, challenges, playground items. View analytics. Manage users. Upload images.
⚠️ Admin Creation

Admin accounts can only be created via the database seed script or by another admin promoting a user through the Admin Users Manager. The registration endpoint always creates users with role: "user".

9.2 Production Deployment (Vercel + Render)

Frontend → Vercel

  1. Push code to GitHub
  2. Go to vercel.com → Import Git Repository
  3. Framework Preset: Vite
  4. Build Command: npm run build (auto-detected)
  5. Output Directory: dist (auto-detected)
  6. Add Environment Variables:
    • VITE_API_BASE_URL = https://your-backend.onrender.com/api
    • VITE_GOOGLE_CLIENT_ID = Your Google OAuth Client ID
  7. Deploy. The vercel.json file handles SPA rewrites automatically.
⚠️ Vite Environment Variables

Vite bakes VITE_* environment variables into the JavaScript bundle at build time. Any change to these variables requires a redeployment to take effect. They are NOT read at runtime.

Backend → Render

  1. Go to render.com → New Web Service
  2. Connect your GitHub repo
  3. Root Directory: backend
  4. Build Command: npm install
  5. Start Command: node server.js
  6. Add ALL environment variables from your .env (see Section 10)
  7. Set NODE_ENV=production
  8. Set FRONTEND_URL = Your Vercel URL (e.g., https://GitHappensqsim.vercel.app)
⚠️ Render Free Tier — Cold Start

On Render's free tier, the backend service spins down after 15 minutes of inactivity. The first request after inactivity takes 30-60 seconds to "cold start." For production use, upgrade to the paid tier ($7/month) to keep the service always running.

9.3 Cloudinary Configuration

Cloudinary is used in production for persistent image storage. In development, images are stored locally in backend/uploads/.

  1. Sign up at cloudinary.com
  2. Get your Cloud Name, API Key, and API Secret from the Dashboard
  3. Set them in the backend environment variables
  4. Images are automatically uploaded to the quantum-sim-lab folder with auto quality and format optimization

9.4 Google OAuth Setup

  1. Go to Google Cloud Console
  2. Create/select a project
  3. Navigate to APIs & Services → OAuth consent screen → Configure → Set User Type to "External" → Publish the app
  4. Navigate to APIs & Services → Credentials → Create OAuth Client ID → Web Application
  5. Add Authorized JavaScript Origins:
    • http://localhost:5173 (development)
    • https://GitHappensqsim.vercel.app (production)
  6. Copy the Client ID and set it as GOOGLE_CLIENT_ID (backend) and VITE_GOOGLE_CLIENT_ID (frontend)

9.5 GNews API Integration

  1. Sign up at gnews.io
  2. Get your API key from the dashboard
  3. Set GNEWS_API_KEY in the backend environment
  4. The backend proxies GNews requests to keep the API key server-side
  5. An in-memory cache (15 min TTL) minimizes API calls

13.2 Caching Strategy

  • Redis Cache: Optional middleware for docs, blogs, news endpoints. TTL: 1 hour. Automatically invalidated on CRUD operations via invalidateCache(keyPrefix).
  • GNews Cache: In-memory Map with 15-minute TTL. Minimizes external API calls to stay within the 100 req/day free tier.
  • Frontend: AlgorithmContext caches the algorithm list in React state to avoid redundant API calls across page navigations.
  • Vercel CDN: Static assets are served from Vercel's global CDN with automatic edge caching.

13.3 Scaling Recommendations

  • Horizontal Scaling: The backend is stateless (no session storage). It can be horizontally scaled behind a load balancer.
  • Python Execution Bottleneck: The quantum execution engine uses child_process.exec(), which is blocking. For high concurrency, consider offloading Python execution to a separate worker service (e.g., AWS Lambda, Cloud Functions, or a dedicated Python microservice with a job queue).
  • Database Indexing: Key indexes are already in place: Algorithm.id, User.username, User.email, PageVisit.path+date.

15. Quantum Execution Engine

15.1 How It Works

  1. User selects an algorithm and configures parameters in the UI
  2. Frontend sends POST /api/run with {algorithmId, parameters}
  3. Backend maps frontend parameter names to Python variable names (e.g., "Number of Qubits" → num_qubits)
  4. Backend constructs a papermill command: 
    python -m papermill "notebooks/grover-search.ipynb" "notebooks/output_TIMESTAMP.ipynb" -p num_qubits 3 -p iterations 1 -k python3
  5. Papermill injects the parameters into the notebook's tagged "parameters" cell and executes all cells
  6. Backend parses the executed notebook's output cells:
    • Images (base64 PNG): Circuit diagrams, histograms, Bloch sphere images
    • Text (stdout): Console output, measurement dictionaries
    • Errors: Stack traces (ANSI color codes stripped)
  7. Backend extracts Bloch sphere angles (θ, φ) from text markers like BLOCH_THETA=1.23
  8. Backend parses measurement dictionaries (e.g., {'101': 500, '010': 524}) into probability distributions
  9. Results returned as JSON: {circuit, graph, blochImage, console, measurements, blochSphere}
  10. Temporary output notebook is deleted after parsing
